  Scenario 2 — E-commerce Order Management (Doc Upload)

  Create a file orders-api.md with this content:

  # Order Management API

  Base URL: https://api.myshop.com/v2

  ## Authentication
  All endpoints require Bearer token in Authorization header.

  ## Endpoints

  ### GET /orders
  Retrieve a paginated list of orders.
  Query params: page (int), limit (int, max 100), status (enum: pending/shipped/delivered/cancelled), customer_id (string, optional)
  Returns: { orders: [], total: int, page: int }

  ### GET /orders/{order_id}
  Get a single order by ID. Returns full order details including line items.

  ### POST /orders
  Create a new order.
  Body: { customer_id: string (required), items: [{ product_id: string, quantity: int, price: float }], shipping_address: { street,
  city, zip, country } }

  ### PATCH /orders/{order_id}/status
  Update order status.
  Body: { status: enum(pending/shipped/delivered/cancelled), tracking_number: string (optional) }

  ### DELETE /orders/{order_id}
  Cancel an order. Only allowed when status is "pending".

  Upload this file via Doc Upload.

  What to check:
  - 5 endpoints parsed correctly
  - GET /orders has query params in input_schema
  - POST /orders has nested items array schema
  - PATCH endpoint captures the enum values for status
  - All should show HIGH confidence since the spec is explicit

  Scenario 4 — User Authentication Service (Doc Upload)

  Create auth-api.yaml:

  openapi: "3.0.0"
  info:
    title: Auth Service API
    version: "1.0.0"
    description: JWT-based authentication service for microservices

  servers:
    - url: https://auth.internal.company.com/api/v1

  paths:
    /auth/register:
      post:
        summary: Register new user
        requestBody:
          required: true
          content:
            application/json:
              schema:
                type: object
                required: [email, password, name]
                properties:
                  email:
                    type: string
                    format: email
                  password:
                    type: string
                    minLength: 8
                  name:
                    type: string
        responses:
          "201":
            description: User created

    /auth/login:
      post:
        summary: Login and get JWT tokens
        requestBody:
          required: true
          content:
            application/json:
              schema:
                type: object
                required: [email, password]
                properties:
                  email:
                    type: string
                  password:
                    type: string
        responses:
          "200":
            description: Returns access_token and refresh_token

    /auth/refresh:
      post:
        summary: Refresh access token
        security:
          - bearerAuth: []
        requestBody:
          required: true
          content:
            application/json:
              schema:
                type: object
                properties:
                  refresh_token:
                    type: string

    /auth/logout:
      post:
        summary: Invalidate tokens
        security:
          - bearerAuth: []

  What to check:
  - base_url auto-filled from servers → HIGH confidence
  - 4 endpoints detected
  - input_schema for /register has email/password/name with types
  - /refresh and /logout have auth flagged as Bearer
  - Overall confidence should be 80%+ since this is a structured OpenAPI spec

  Scenario 5 — CRM Lead Scoring (Chat Builder)

  annual revenue, number of employees, and industry vertical. The system should return a lead score from 0-100 and a tier

  - PUT /scoring-weights should have a different auth_type (admin key) — LOW/MEDIUM confidence here since it's ambiguous
  - Edit the base_url to https://crm.yourcompany.com/api/v1 before saving
